# 轮廓接管加走廊质量门 + 拐点只在可靠走廊上触发

数据：`20261117_191548_21683`（581 帧 / 43.2 s，丢线仅 3 帧 = 0.5%）。现象：环岛前丢线不搜回、车以 0.5~0.65 m/s“随意前进”；之后的 S 弯更差。

## 数据

- CSV 里 `source=road reason=contour_takeover` 共 **312 帧**，速度一路回到 0.65 m/s，`w` 在 S 弯摆到 ±2.0；黑线丢时从不进入 `active_search`（因为接管路径一直“有效”）。
- 拐点拉线也在误触发：f186 起 `corner_entry_pull`（当时在空地上），f286 起 `corner_exit_pull`（S 弯），把车往左拉。
- 离线复算 581 帧的连通域走廊：`single_edge 474 / open_area 79 / width_unstable 21 / branched 6 / no_connected_road 1`，**可靠走廊 0 帧**。即这个场地的白地面是一大片、蓝胶带只是地贴分隔，不是封闭车道；“白−蓝”连通域在大多数帧里是一个很宽/单边的区域。

## 根因（轮廓法常识）

上一版把“最大的白色连通域”当成车道中心线，缺少轮廓巡线必须的约束：

1. 必须同时看到左右两条边（单边不能算中线）；
2. 车道宽度必须合理且沿行稳定（宽大厅不是车道）；
3. 分叉/多段行不能当单车道；
4. 时间上只能短时接管，黑线真的丢了要回搜索，不能一直“有路”；
5. 拐点只在可靠车道上才能用来拉线。

## 修复

- `patrol_contour_line.py` 新增走廊质量：`dual_fraction`（两侧真实边界比例）、`width_ratio/width_mad_ratio`（宽度中位数/离散度）、`branch_ratio`（多段行比例）、`area_ratio`（连通域占屏比）；门限：dual≥0.55、宽 0.18~0.80、宽 MAD≤0.22、分叉≤0.10、面积≤0.85，否则 reason=`open_area/single_edge/too_wide/width_unstable/branched`，`corridor=False`。
- 节点接管只在 `corridor` 且**距最近黑线 ≤0.35 s**、且接管总时长 ≤0.60 s 时启用；之后回普通搜索（不再长期替代黑线）。
- `CornerRingState` 只在 `corridor` 上触发；出环还要求入环后 ≥1.5 s、且没有黑线。
- 新增参数 `contour_takeover_max_seconds=0.60`、`contour_takeover_max_gap_seconds=0.35`、`contour_corner_min_ring_seconds=1.50`；调试预览显示 `corr/dual/w/mad/br`。
- 8 条单测：走廊/宽大厅/单边、拐点几何、状态机、非可靠走廊不触发、冷却、参数校验。

## 结果

- 同一段采集按新门复算：**0 帧**满足走廊 → 接管和拐点拉线都不会触发 → 车回到“黑线 + 丢线搜索”的旧行为，不再随意前进。
- 参考视频 2433 帧同样 0 帧走廊（single_edge 1569 / open_area 853）——说明这套“白−蓝连通域”在本赛道不能当车道边界；要让轮廓法真正参与，需要改用**蓝胶带/道路双边**作为边界（现有 `road_centerline` 已有双边宽度逻辑，可复用），或者换一种“左右边线”定义。

## 下一步（需确认）

1. 方案 A（保守）：保留本次门控，轮廓链只做诊断，不参与控车；车回到已验证的黑线巡线。
2. 方案 B（推荐）：把边界来源改成蓝胶带/道路双边（复用 `road_centerline` 的双边 + 宽度先验），再在这条“真车道”上做拐点拉线；这样才会在实车出现可用的左右边线。
3. 方案 C（临时验证拐点）：临时把 `corridor` 放宽为“单边+宽度先验”，只开 0.6 s 接管，接受误触发风险，用来采集拐点视频；不建议直接比赛用。
